## User Scenarios & Testing *(mandatory)*

本特性的「用户」是底座内部的调用方（后续的 ReAct 循环）与部署运维人员。它本身没有面向终端用户的入口，端到端 Demo 一要等 US-2 完成后一起验（AiProgrammingGuide §4.1）。因此每个故事的独立测试都通过调用方视角的集成测试完成。

### User Story 1 - 通过统一入口完成一次模型对话 (Priority: P1)

运维人员在配置里登记一家模型服务（例如 DeepSeek），给出 provider 名、模型名、引用环境变量的 API key。调用方传入「用哪家」和一组对话消息，拿到模型回复文本和本次 token 用量，不需要知道这家服务的协议细节。

**Why this priority**: 没有 LLM 调用，后续所有 Agent 能力都跑不起来（AiProgrammingGuide §1「US-1 是基础」）。这是最小可用切片。

**Independent Test**: 只配置一家服务，调用方发一条「你好」，能拿到非空回复和 token 用量；把 API key 环境变量去掉后重启，启动失败且报错指明缺哪个变量。

**Acceptance Scenarios**:

1. **Given** 已登记 provider `deepseek` 且其 API key 环境变量有值，**When** 调用方以 `deepseek` 发送一组对话消息，**Then** 返回模型回复文本，且附带输入、输出与总 token 数。
2. **Given** 配置中 API key 写成环境变量引用而该变量未设置，**When** 启动服务，**Then** 启动失败，错误信息指出 provider 名与缺失的变量名，且不输出任何凭证内容。
3. **Given** 已登记的服务调用时网络失败或返回错误，**When** 调用方发起调用，**Then** 调用方立即收到可识别的失败（含 provider 名与原因），平台不自动换用其他服务重试。

---

### User Story 2 - 多家模型服务并存时按名称精确路由 (Priority: P2)

运维人员同时登记 DeepSeek 与 Kimi（以及将来更多），各自有唯一 provider 名。不同 Agent 的配置按 provider 名引用，调用总是落到被点名的那一家，不会因为各家服务「长得一样」而路由错乱。

**Why this priority**: 多模型并存是企业底座的基本诉求（需求 §5.3），也是验收硬条件（需求 §13「至少跑通 DeepSeek 和 Kimi 两个」）。依赖 US1 的单家调用。

**Independent Test**: 同时登记两家，分别以两个名字各调用一次，确认每次请求只打到对应服务的端点（可用桩服务观察请求落点）；用一个未登记的名字调用，得到明确错误。

**Acceptance Scenarios**:

1. **Given** 同时登记 `deepseek` 与 `kimi`，**When** 调用方先后以两个名字调用，**Then** 两次请求分别只到达对应服务，返回结果互不串台。
2. **Given** 只登记了 `deepseek`，**When** 调用方以 `qwen` 调用，**Then** 返回「provider 未登记」错误并列出已登记名，不静默落到任何一家。
3. **Given** 配置里两条记录使用同一个 provider 名，**When** 启动服务，**Then** 启动失败并指出重名。

---

### User Story 3 - 每次模型调用留下审计记录 (Priority: P2)

审计人员需要事后回答「哪个会话、在什么时候、调了哪家哪个模型、花了多少 token、用了多久」。每一次模型调用（成功或失败）都留下一条持久化记录，进程重启后仍可查到。

**Why this priority**: 可审计是 OryxOS 的核心差异化能力，宪法原则 V 要求 day one 落库、不得以日志代替。与 US2 同级，依赖 US1。

**Independent Test**: 发起两次成功调用和一次失败调用，直接查看持久化存储，确认恰好新增三条记录且字段完整；重启后记录仍在。

**Acceptance Scenarios**:

1. **Given** 调用方携带会话标识发起一次成功调用，**When** 调用完成，**Then** 存储中新增一条记录，含会话标识、provider、模型、输入/输出/总 token、耗时、时间。
2. **Given** 一次调用因服务端错误失败，**When** 调用结束，**Then** 依然新增一条记录，耗时如实记录，token 缺失时记为空而不是编造。
3. **Given** 审计存储暂时不可写，**When** 发生一次模型调用，**Then** 调用结果照常返回给调用方，同时输出一条可告警的错误日志（审计失败不阻断业务，但不能静默吞掉）。

---

### User Story 4 - 把工具描述交给模型，并把工具调用请求原样交回 (Priority: P3)

调用方（后续 ReAct 循环）把本轮可用的工具清单（名称、说明、参数结构）随消息一起交给模型。模型如果决定调用工具，平台把「调哪个工具、带什么参数、调用编号」原样交回调用方，平台自己不执行任何工具。

**Why this priority**: US-1 自身不依赖它也能对话，但 US-2（ReAct 循环）的每一轮都要用到。必须在本特性内把边界钉死，防止工具被平台和调用方各执行一次（宪法原则 I/II）。

**Independent Test**: 交给模型一个「查天气」工具并提问天气，确认返回的结构里带有工具名、参数和调用编号，同时确认该工具的执行计数为 0。

**Acceptance Scenarios**:

1. **Given** 调用方提供一个工具描述且问题需要它，**When** 模型决定调用该工具，**Then** 调用方收到一条或多条工具调用请求（工具名、参数、调用编号），平台对该工具的执行次数为 0。
2. **Given** 调用方把上一轮的工具执行结果作为消息回填，**When** 再次调用，**Then** 模型能基于该结果继续回答（消息中工具结果与原调用编号对应）。
3. **Given** 不提供任何工具，**When** 调用，**Then** 行为与 US1 一致，不出现工具调用请求。

---

### Edge Cases

- API key 环境变量存在但为空字符串：按「缺失」处理，启动失败。
- 未配置 base URL：使用该服务的公开默认地址；配置了则以配置为准（私有化网关场景）。
- 调用方传入空消息列表：直接拒绝，不发起外部调用，也不写审计（没有发生模型调用）。
- 模型响应缺少 token 用量字段：回复照常返回，审计中 token 字段记为空。
- 模型同一轮既返回文本又返回工具调用：两者都交回，由调用方决定如何处理。
- 模型返回多个工具调用：全部按顺序交回，保留各自调用编号。
- 外部服务长时间无响应：在可配置的超时后以失败返回，并写一条失败审计。
- 两个调用方并发调用同一家服务：互不阻塞、互不串数据，各自一条审计记录。
- 配置中直接写了 API key 明文（不是环境变量引用）：拒绝启动，提示改为环境变量引用。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持登记多个模型服务，每个服务的配置项为：唯一 provider 名、默认模型名、API key、可选 base URL。
- **FR-002**: 系统 MUST 提供统一调用入口：输入为 provider 名、模型名（可选，缺省用该服务默认模型）、对话消息列表、可选工具清单、可选会话标识；输出为回复文本、工具调用请求列表、token 用量。
- **FR-003**: 系统 MUST 按调用方指定的 provider 名路由到被登记的那一家服务，且只能通过名称确定路由目标，不得根据服务实现的类型推断。
- **FR-004**: 对未登记的 provider 名，系统 MUST 返回明确错误并列出当前已登记的名称。
- **FR-005**: API key MUST 只能以环境变量引用的形式出现在配置中，系统在启动时解析并校验。必填项缺失、为空或格式非法时，启动失败，错误信息指出 provider 名与问题项。
- **FR-006**: 系统 MUST NOT 在日志、错误信息、审计记录中输出 API key 明文。
- **FR-007**: 系统 MUST 把调用方提供的工具清单（名称、说明、参数结构）转换成目标服务能理解的格式，调用方不需要关心各家格式差异。
- **FR-008**: 模型返回工具调用请求时，系统 MUST 把每个请求的工具名、参数、调用编号原样交回调用方，且 MUST NOT 自行执行任何工具或自动发起后续轮次。
- **FR-009**: 系统 MUST 支持调用方把工具执行结果作为消息回填，并与原调用编号对应，以便下一次调用继续推理。
- **FR-010**: 每一次实际发起的模型调用（成功或失败）MUST 写入一条持久化审计记录，字段为：会话标识（可空）、provider 名、模型名、输入/输出/总 token 数（可空）、耗时（毫秒）、调用时间。
- **FR-011**: 审计写入失败 MUST NOT 改变调用结果，但 MUST 输出错误级别日志。
- **FR-012**: 外部服务调用失败或超时时，系统 MUST 立即向调用方返回可识别的失败（含 provider 名与原因），MUST NOT 自动切换到其他服务或并发竞速（核心阶段不做 fallback / hedge racing）。
- **FR-013**: 系统 MUST 支持并发调用，同一服务的并发请求互不阻塞、互不串数据。
- **FR-014**: 提供商配置变更在重启后生效（需求 §8.3），核心阶段不要求热更新。

### Key Entities *(include if feature involves data)*

- **Provider 配置**：一家模型服务的登记信息。provider 名（唯一键）、默认模型名、API key 引用、可选 base URL、调用超时。
- **模型调用请求**：一次调用的输入。目标 provider 名、模型名、有序消息列表、工具清单、会话标识。
- **对话消息**：角色（系统 / 用户 / 助手 / 工具结果）+ 内容；工具结果消息带对应的调用编号。
- **工具描述**：名称、用途说明、参数结构；只描述，不含执行逻辑。
- **工具调用请求**：模型产出的「想调某工具」，含调用编号、工具名、参数。
- **模型调用结果**：回复文本、工具调用请求列表、token 用量。
- **LLM 调用审计记录**：一次实际模型调用的事实记录，字段见 FR-010；与会话通过会话标识关联。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同时登记两家服务（DeepSeek、Kimi），调用方只改 provider 名即可在两家之间切换，调用方代码改动行数为 0，两家各至少成功完成 1 次真实对话。
- **SC-002**: 用 100 次混合成功与失败的调用做核对，持久化审计记录条数与实际发起的调用次数一致（100%），必填字段缺失为 0。
- **SC-003**: 凭证缺失或重名配置时，服务在 10 秒内启动失败，且一条错误信息即可定位到 provider 名和问题项。
- **SC-004**: 在全部测试产生的日志、错误信息、审计记录中检索测试用 API key，命中次数为 0。
- **SC-005**: 模型返回工具调用请求的场景下，平台执行工具的次数为 0，调用方收到的工具名、参数与模型原始输出一致。
- **SC-006**: 使用本地桩模型服务时，平台在单次调用上附加的开销 P99 ≤ 50ms（需求 §8.1「内部转发开销」）。
- **SC-007**: 对未登记 provider 名的调用，100% 返回明确错误，且没有任何请求到达任一外部服务。

## Assumptions

- DeepSeek 与 Kimi 都提供 OpenAI 兼容协议（需求 §8.4 视其为事实标准），且有可用的测试账号与 API key。
- 核心阶段只做非流式、同步的单次调用；流式输出放扩展阶段（宪法原则 VII）。
- 审计记录写入项目默认的嵌入式持久化存储。本特性只要求写入，查询接口与成本看板放扩展阶段（技术方案 §3.3）。
- 无状态调用（如单次 invoke）没有会话标识，审计记录中该字段为空。
- 调用超时默认 60 秒，可按 provider 配置覆盖。
- 本特性不负责 Agent 配置文件（`AGENT.md` frontmatter）如何引用 provider 名，只保证「给定 provider 名即可调用」。引用解析属于 Profile 加载，由后续特性完成。
- 本作业把四份文档当作 greenfield 输入，不以仓库现有实现为准（差异见 `research.md`）。
