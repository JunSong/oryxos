# 什么是 Agent：从 Hermes Agent 与 OryxOS 的对照说起

> 这是一份技术思考笔记，不是选型建议，也不评判谁更好。目的只有一个：借两个设计取向不同的项目，把「Agent 到底是什么」拆到不能再拆。
>
> 资料口径：Hermes Agent 以其中文社区文档为准（[功能概览](https://hermesagent.org.cn/docs/user-guide/features/overview)、[持久记忆](https://hermesagent.org.cn/docs/user-guide/features/memory)、[技能系统](https://hermesagent.org.cn/docs/user-guide/features/skills)、[子 Agent 委派](https://hermesagent.org.cn/docs/user-guide/features/delegation)、[工具与工具集](https://hermesagent.org.cn/docs/user-guide/features/tools)，上游为 [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)）；OryxOS 以本仓库 0.1.8 的代码与文档为准。两者都在快速迭代，具体数字（字符上限、并发数等）以各自最新文档为准。

## 一、Agent 是什么

### 1.1 从最小事实出发

大语言模型（LLM）本身只做一件事：**给定一段上下文，输出下一段文本**。它是一个无状态的函数：

```
output = LLM(context)
```

它不记得上一次调用，也不能自己读文件、跑命令或发消息。能做的只有一件事：在输出里**表达一个意图**，比如「我想调用 `read_file`，参数是 `/etc/hosts`」。这就是 Function Calling，本质是一种约定好的输出格式。

所以，「模型」和「能做事的系统」之间隔着一层：得有人去**解释**模型的意图、**执行**动作、把**结果**塞回下一次的上下文，再问模型「然后呢」。这一层就是 Agent 的运行时，业界也叫 **harness**（缰绳、挽具）。

### 1.2 Agent 的最小定义

把上面的事实写成循环，就是 Agent：

```
context ← 组装(指令, 记忆, 历史, 可用工具)
loop:
    decision ← LLM(context)
    if decision 是最终回答: 结束
    result  ← 在边界内执行(decision.动作)
    context ← context + decision + result
    if 超出步数/预算: 按策略收尾
```

**Agent 是「由模型决定下一步」的控制循环。** 模型负责「想」，运行时负责「做」和「记」。这和普通程序的区别只在一点：控制流的下一跳由模型的输出决定，而不是由程序员事先写死。

据此，任何 Agent 系统都可以拆成七个正交的部件：

| 部件 | 回答的问题 | 典型实现 |
|------|-----------|---------|
| **模型（Model）** | 谁来判断下一步 | 一个或多个 LLM，加上路由与备用切换 |
| **循环（Loop）** | 怎么迭代、何时停 | ReAct 循环、最大步数、中断、收敛策略 |
| **上下文（Context）** | 这一轮让模型看到什么 | 系统提示、指令文件、记忆、历史、工具清单 |
| **动作（Tools）** | 模型能对世界做什么 | 文件、Shell、HTTP、浏览器、MCP、子 Agent |
| **状态（State）** | 跨轮次、跨会话留下什么 | 会话历史、长期记忆、技能、检索库 |
| **边界（Boundary）** | 动作可以碰到哪里 | 沙箱、白名单、容器、审批、权限 |
| **触发（Trigger）** | 循环由谁、在何时启动 | 人发消息、定时任务、事件、另一个 Agent |

### 1.3 一个关键洞察：上下文窗口是唯一的「工作台」

模型每一轮能用的信息，只有这一轮上下文窗口里的内容。窗口有长度上限，每个 token 都有成本，内容越多，模型的注意力也越分散。

因此，几乎所有 Agent「功能」最终都在回答两类问题：

1. **上下文工程**：这一轮把什么放进窗口、什么不放、什么按需再取？记忆、技能、渐进式披露、会话检索、子 Agent 隔离、上下文压缩，都是这一类。
2. **动作治理**：模型输出的动作由谁执行、在什么边界内执行、留下什么记录？沙箱、终端后端、审批、审计、权限，都是这一类。

后文对比两个项目时，可以反复用这两个问题去对照。

### 1.4 自主度是一条光谱，不是一个开关

「Agent」不是非黑即白的概念。按「控制流有多少交给模型」排开：

```
固定流水线 ── 带 LLM 节点的工作流 ── 单步工具调用 ── ReAct 循环 ── 可委派子任务 ── 可自我修改技能/记忆
   (程序决定)                                                              (模型决定得越来越多)
```

越往右，模型决定得越多：灵活性更高，可预测性更低，对边界和观测的要求也更高。两个项目都覆盖了这条光谱的多个点（Hermes 有 `execute_code` 这类机械流水线，也有能自我改写技能的 Agent；OryxOS 有 Flow DSL，也有 ReAct 循环和团队编排），只是**默认站位**不同。

## 二、两个项目在七个部件上的映射

先给一张总表，后面分功能、架构、企业价值三个角度展开。

| 部件 | Hermes Agent | OryxOS |
|------|-------------|--------|
| 模型 | 多 Provider；提供者路由、备用提供者、凭证池（同一提供者多 key 轮换） | 多 Provider 显式映射；按序备用切换；预算降级与成本路由 |
| 循环 | Python 实现的 Agent 循环；子 Agent 默认最多 50 轮 | 自实现 `ReActLoop`；默认 `max_iterations` 10，按 Agent 配置 `error`/`summarize` 收敛 |
| 上下文 | 自动发现 `.hermes.md`/`AGENTS.md`/`CLAUDE.md`/`SOUL.md`/`.cursorrules`；`@` 引用内联展开 | `AGENT.md` 正文 + Bootstrap（`AGENTS.md`/`SOUL.md`/`USER.md`）+ 技能元数据 + 记忆 + 历史，每轮组装 |
| 动作 | 丰富内置工具集（网络、终端、文件、浏览器、视觉、语音、Home Assistant 等）+ MCP + 插件 | 内置文件/Shell/HTTP/通知/记忆/知识检索等 + MCP + Java `@Tool`；`delegate_agent`、`execute_code`、`a2a_send` |

| 边界 | 终端后端（local/docker/ssh/singularity/modal/daytona），容器硬化；记忆与技能安装前做安全扫描 | 路径/命令/域名/SMTP 白名单；工具策略层（全局/按 Agent allow/deny）；高风险审批（HITL）；RBAC；可选 docker/ssh 执行后端 |
| 触发 | CLI、消息平台网关、自然语言 Cron、事件钩子、OpenAI 兼容 API、IDE（ACP） | CLI、REST API（含 SSE）、18 个 IM 入站渠道、frontmatter 声明的日程、Flow、A2A |

## 三、功能角度

这里不按「谁功能多」比较，而是看每个部件上**各自解决的是哪个问题**。

### 3.1 记忆：什么该留在窗口里

**Hermes** 把记忆分成两层，边界很清楚：

- **常驻层**：`MEMORY.md`（Agent 的笔记，约 2,200 字符）和 `USER.md`（用户画像，约 1,375 字符），会话开始时作为**冻结快照**注入系统提示。会话中途写入会立即落盘，但下个会话才进入提示。这么做是为了保住 LLM 的前缀缓存（prefix cache）。容量满了由 Agent 自己合并、替换条目。
- **检索层**：所有会话进入 SQLite 并建 FTS5 全文索引，`session_search` 按需搜索，再由模型做摘要。另可外接 Honcho、Mem0 等记忆提供者做用户建模。
- 写入前扫描提示注入、凭证外泄、不可见 Unicode 字符。

**OryxOS** 的记忆同样是「常驻 + 检索」两层，但切分方式不同：

- **常驻层**：`MEMORY.md` 每轮注入，超过 4,000 字截断保留最近部分；`USER.md` 由人写、系统只读。
- **检索层**：`recall_memory` 检索归档记忆，配置 embedding 后做语义、关键词、时间三路加权融合。另有独立的**知识库**（文档解析、切分、向量化、双路召回 + RRF），把「Agent 学到的」和「组织给定的资料」分成两件事。
- 后端可选 Markdown 文件或数据库，集群模式下记忆走共享存储。

**背后的问题是同一个**：常驻记忆贵（每轮都占 token），检索记忆便宜但可能漏召回。Hermes 用硬性字符上限，逼 Agent 自己做「记忆编辑」；OryxOS 用截断兜底，把「资料」外移到知识库。冻结快照和每轮重新组装也是一组取舍：前者换来缓存命中和稳定性，后者换来同一会话内的即时可见。

### 3.2 技能：程序性记忆归谁管

两者都采用 agentskills.io 兼容的 `SKILL.md` 格式和**渐进式披露**：先只给模型「名称 + 描述」，命中后再读正文，需要时再读附属文件。这一点上，两者对上下文工程的认识一致。

差异在**技能的所有权和写入权**：

- **Hermes**：技能就是 Agent 的**程序性记忆**。Agent 可以用 `skill_manage` 自己创建、修补、删除技能，触发时机包括完成 5 次以上工具调用的复杂任务、走出死胡同、被用户纠正之后。另有技能中心，可从官方源、skills.sh、GitHub、ClawHub 等安装，安装时做安全扫描并分信任等级（builtin / official / trusted / community）。技能还会自动变成斜杠命令。
- **OryxOS**：技能是**公共资产**，统一放在 `.oryxos/skills/`，每个 Agent 通过 `agents/<name>/skills/` 下的相对软连接决定「能看见哪些」；软连接集合就是唯一的绑定关系。增删改走管理面，并有悬空链接、越界链接、名称不匹配等巡检；被引用的技能默认禁止删除。「从经验中自动沉淀技能」在路线图里，目前不是默认行为。

**背后的问题**：Agent 能否修改自己的行为规则？允许修改，Agent 就能越用越顺手，代价是行为会随时间漂移，需要事后审视它改了什么；不允许修改，行为可复现、可评审，代价是改进要靠人来做。这是 1.4 节那条自主度光谱在「状态」这个部件上的具体位置。

### 3.3 工具与执行：模型的手伸多远

- **Hermes** 的工具面很宽：网络搜索与抽取、终端（含后台进程和 PTY）、文件补丁、浏览器自动化、视觉、图像生成、TTS、Home Assistant、强化学习训练。工具按**工具集**组织，可按平台开关。执行位置由**终端后端**决定，从本机到 Docker、SSH、HPC 容器、无服务器云沙箱共六种；容器后端默认只读根文件系统、移除所有 capability、限制 PID。`execute_code` 让模型写一段 Python，通过 RPC 调用一小组工具，把多步机械操作压缩成一次 LLM 调用。另有检查点与 `/rollback`，修改文件前自动快照。
- **OryxOS** 的内置工具偏「后台业务」：文件、Shell、HTTP、通知、记忆、知识检索、Excel 导出等，外加 MCP（stdio、Streamable HTTP）和 Java `@Tool`。执行边界由 `SandboxChecker` 白名单决定：路径要用 `toRealPath()` 校验真实位置，Shell 只认精确的可执行文件名、参数以 argv 直传不经 Shell 解释，HTTP 走 SSRF 黑名单或域名白名单，SMTP 按端点放行。白名单之上还有独立的**工具策略层**（「这个 Agent 能不能用这个工具」）和**审批层**（高风险动作先挂起、推给人批准）。`execute_code` 可跑在 docker 或 SSH 后端。

**背后的问题**：边界画在「环境」上还是「动作」上？Hermes 主要把边界画在**执行环境**上：在一个隔离好的盒子里，Agent 可以做很多事。OryxOS 主要把边界画在**每个动作的参数**上：哪个文件、哪条命令、哪个域名，逐项判断，再叠加策略和审批。前者对开放式任务更友好，后者对「谁对哪个动作负责」更容易落到记录上。两者正在互相靠拢：Hermes 也有工具集开关，OryxOS 也有容器后端。

### 3.4 多 Agent：拆任务还是拆角色

- **Hermes** 的 `delegate_task` 解决的是**上下文隔离**。子 Agent 从一张白纸开始，只拿到 `goal` 和 `context`，跑完只把摘要交回父 Agent，以免父 Agent 的窗口被淹没。最多 3 个并行、深度为 2（子 Agent 不能再委派），子 Agent 被禁止写共享记忆、发消息、调用 `execute_code`。子 Agent 可以用更便宜的模型。
- **OryxOS** 有三种组织方式：
  - `delegate_agent`：进程内把任务交给另一个**已声明的 Agent**，也就是另一份 `AGENT.md`，有自己的指令、工具和策略。
  - **团队任务**：协调者规划、专家并行扇出、按 after/dependsOn 分波次调度、失败有界重规划、可挂起等待人工审批、成本归因、持久化。
  - **Flow**：用 Markdown DSL 声明节点和边，节点可以是 Agent、工具或团队任务。
  - 另外，**A2A** 协议支持跨实例发现和委托。

**背后的问题**：子 Agent 是「同一个 Agent 的临时分身」，还是「另一个有身份的 Agent」？前者主要省上下文，后者主要分职责。两种都成立，回答的是不同问题。

### 3.5 触发与交互面：Agent 在哪里被叫醒

- **Hermes** 的交互面围绕**一个人**展开：CLI 与 TUI 皮肤、各消息平台、语音对话（含 Discord 语音频道）、图片粘贴、IDE（ACP），以及把自己暴露成 OpenAI 兼容端点，接入 Open WebUI 等前端。自动化有自然语言 Cron 和事件钩子。批量处理可以并行跑成千上万条提示，产出训练轨迹。
- **OryxOS** 的交互面围绕**一个组织**展开：REST API 是一等入口（会话、无状态调用、SSE 流式）、18 个 IM 入站渠道（飞书、企微、钉钉、微信系、Slack、Teams、Telegram 等）、Web 管理台、frontmatter 里声明的日程、Flow、A2A。入站 Webhook 可要求调用方令牌，集群模式下强制校验。

## 四、技术架构角度

### 4.1 「一个 Agent」是什么形态

这是两者最根本的差别，其余差异大多由此派生。

- **Hermes**：Agent 是**一个持续成长的个体**。一个 `~/.hermes/` 目录就是它的全部：配置、记忆、技能、会话库。它跟随一个用户，在使用中不断积累（记忆、技能、用户画像）。要隔离多个用户或场景，就再起一个实例或换一个 home 目录。
- **OryxOS**：Agent 是**一份可部署的声明**。`.oryxos/agents/<name>/AGENT.md` 的 frontmatter 声明模型、工具、渠道、日程和设置，正文写任务指令。一个运行时同时加载多个这样的声明，共享渠道、模型路由、工具、记忆基础设施和审计。Agent 的行为主要由声明决定，而不是由使用历史决定。

可以类比：前者像一个跟着你学习的私人助理，后者像一个岗位说明书，可以招很多人来照着做。两者都是 Agent，只是「身份」挂在不同的东西上：一个挂在**累积的状态**上，一个挂在**声明的配置**上。

### 4.2 进程、语言与并发

| 维度 | Hermes Agent | OryxOS |
|------|-------------|--------|
| 语言 | Python | Java 21 + Spring Boot |
| 并发模型 | 线程池（如子 Agent 并行用 `ThreadPoolExecutor`） | 同步阻塞 + 虚拟线程，明确不引入 Reactor 一类异步模型 |
| 部署单元 | 单用户进程，本机优先；可通过网关常驻 | 服务进程；单机零配置（SQLite），也可多副本 + PostgreSQL + 共享卷，提供 Helm Chart |
| 配置 | `~/.hermes/config.yaml` + `.env` | `AGENT.md` frontmatter + 应用配置 + 数据库（Provider、渠道、策略可在管理台热更新） |
| 扩展 | 插件（工具、钩子、记忆提供者、上下文引擎）、MCP、技能中心 | MCP、Java `@Tool` Bean、渠道模块、存储插件；契约放 `oryxos-core`，下游实现（依赖倒置） |

Python 生态和 AI 研究工具链贴得近，适合快速接入新模型和新能力（Hermes 的强化学习训练、轨迹生成就是这种贴近的体现）。Java 生态和企业后端贴得近，适合嵌进已有的服务治理、监控、身份体系。这是生态位的差异，不是语言优劣。

### 4.3 状态放在哪里

- **Hermes**：状态是**本地文件 + 本地 SQLite**（`~/.hermes/state.db`）。简单、可读、可直接编辑，迁移就是拷目录；代价是天然单机。
- **OryxOS**：状态分两面。**文件面**（Agent、技能、人格、知识）放工作区，集群模式下放共享卷，用版本号总线让各副本感知变化。**数据面**（会话、审计、策略、成本、调度）进数据库，跨副本的「恰好一次」靠 CAS 认领实现，包括会话轮次租约、调度到点认领、渠道连接属主。代价是更多的部件，以及对数据库和共享存储的依赖。

这对应「无状态实例，状态外置」这条设计原则：只要实例不持有状态，就能横向扩展；而状态一旦外置，就必须处理并发和一致性。

### 4.4 循环的所有权

- **Hermes** 的循环由框架自己实现，围绕单个 Agent 做了大量体验优化：中断传播（用户发新消息即打断所有子 Agent）、后台进程、记忆冻结快照保缓存、子 Agent 只回摘要。
- **OryxOS** 把「自实现 ReAct 循环」写成了项目宪法：Spring AI 只用来做 Provider 协议转换和 `@Tool` 的 schema 生成，明确禁止它自动执行工具，避免工具被执行两次，也让每次工具调用都经过同一条「沙箱 → 策略 → 审批 → 执行 → 审计」路径。循环中断时会补齐缺失的工具结果，防止会话卡死。

两者都选择自己掌握循环。这说明一个事实：**循环是 Agent 的心脏，交给通用框架自动执行，就很难在每一步插入自己的规则。**

### 4.5 可观测性：看过程还是看责任

- **Hermes** 的观测更偏向**运行过程与数据**：CLI 里用树形视图实时显示子 Agent 的工具调用；批量处理产出 ShareGPT 格式的轨迹，可用于训练和评测。
- **OryxOS** 的观测更偏向**留痕与归因**：`tool_invocations`、`llm_calls` 两张审计表从第一天就落库，同一个 `trace_id` 串起一轮处理的模型调用、工具调用和执行记录；可选导出 OTel trace；有成本账本、预算配额、成本看板；还能把审计轨迹导出为评测用例。

两者都在回答「Agent 刚才做了什么」，只是服务的读者不同：一个主要给使用者和训练者看，一个主要给运维、审计和财务看。

---

## 五、企业价值角度

「企业价值」很容易写成推销。**一个组织引入 Agent 时，会面对哪些在个人使用中不存在、或不突出的问题？** 再看两个项目各自站在什么位置、要付出什么代价。

### 5.1 从个人到组织，多出来的问题

| 问题 | 个人场景 | 组织场景 |
|------|---------|---------|
| 谁拥有 Agent | 使用者自己 | 部门或平台团队；使用者和拥有者常常不是同一个人 |
| 谁为动作负责 | 使用者自己承担后果 | 要能回答「哪个 Agent、受谁委托、在什么时间、做了什么、花了多少钱」 |
| 数据边界 | 个人数据、个人凭证 | 多人共享一个 Agent，记忆和会话可能跨越权限边界 |
| 行为变更 | 越用越顺手是好事 | 行为变更需要评审、回滚、复现 |
| 规模 | 一个人、一台机器 | 多个 Agent、多个渠道、多个副本，要求高可用 |
| 成本 | 自己的账单 | 要归因到团队或任务，要有预算和配额 |
| 集成 | 个人工具、个人账号 | 企业 IM、SSO、已有业务系统、K8s |

### 5.2 两者在这些问题上的位置

**Hermes 的价值重心在「单个 Agent 的能力与成长」**：

- 开箱即用的工具面很宽，交互形态丰富（语音、视觉、IDE、多消息平台）。
- 能从使用中积累记忆和技能，对知识工作者、开发者、研究者这类**以个人生产力为单位**的场景，提升直接而明显。
- 技能中心和插件体系能快速吸收社区能力，并为第三方内容提供安全扫描和信任分级。
- 在团队里使用时，可以每人或每个场景一个实例；组织层面的身份、授权、集中审计需要另行搭建，社区已有第三方加固方案。

**OryxOS 的价值重心在「多个 Agent 的统一底座与治理」**：

- 一个运行时承载多个业务 Agent，共享渠道、模型路由、工具、记忆和知识基础设施，新增 Agent 主要是新增一个目录。
- 治理能力内建：审计落库、工具策略、高风险审批、RBAC、SSO/OIDC、凭证加密存储、成本账本、多副本、Helm 交付。这些直接对应 5.1 表中组织场景的各行。
- 代价同样明显：部件多，配置面大，单个 Agent 的「开箱体验」和工具丰富度不是它的重心；Agent 的改进主要靠人维护声明和技能，而不是自动积累。

### 5.3 一个中性的结论

两者对应的是**同一个公式在不同参数下的两种解**：

- 当「Agent 的主人 = Agent 的使用者 = 后果的承担者」时，最重要的变量是 Agent 本身的能力和成长，治理可以很轻。Hermes 的设计在这个前提下是自洽的。
- 当这三者分离时，最重要的变量变成了边界、归因和一致性，单个 Agent 的能力反而退居其次。OryxOS 的设计在这个前提下是自洽的。

现实中的组织往往两种需求并存：员工个人需要强助理，业务流程需要可治理的 Agent。因此这两类项目更像是**不同层次的东西**，而非同一赛道上的替代品。是否适用，取决于要解决的是哪个人的、哪个问题。

## 六、回到 Agent：从对照中得到的几条认识

**1. Agent 不是模型，也不是一段 prompt，而是「模型驱动的控制循环」加上它的运行环境。** 同一个模型放进 Hermes 和 OryxOS，会表现出完全不同的「Agent」，因为上下文、工具、状态、边界和触发都不同。模型决定上限，harness 决定实际表现。

**2. 几乎所有 Agent 功能，都可以归到「上下文工程」或「动作治理」两类。** 记忆、技能、渐进式披露、会话检索、子 Agent 隔离、冻结快照，回答的是「这一轮窗口里放什么」；沙箱、终端后端、策略、审批、审计，回答的是「模型的意图由谁、在哪里、按什么规则变成现实」。拿到任何一个新的 Agent 产品，用这两个问题去拆，基本都能看清它在做什么。

**3. 状态的类型，决定了 Agent 的「身份」挂在哪里。** 情节记忆（会话）、语义记忆（事实、画像、知识库）、程序性记忆（技能）是三种不同的东西。允许 Agent 自己写程序性记忆，它就会成为一个「会成长的个体」；把程序性记忆交给人维护，它就成为一份「可复现的声明」。

**4. 自主度和可控性是同一条轴的两端，没有免费的位置。** 让模型决定得越多（自建技能、递归委派、开放式工具），就越需要更强的边界和更好的观测。Hermes 给子 Agent 限深度、禁写记忆、禁发消息；OryxOS 给工具加策略和审批。双方都在同一条轴上找各自的平衡点。

**5. 两个项目共同面对、都还没有彻底解决的问题，恰恰是 Agent 的本质难题：**

- **上下文预算**：信息永远比窗口多，取舍本身就需要判断力。
- **可靠性**：每一步都是概率性的，步数越多，累积误差越大；所以才需要最大步数、收敛策略、重规划。
- **注入与越权**：Agent 读到的任何外部内容都可能变成「指令」；所以才需要扫描、白名单、审批。
- **评估**：行为是开放的，「做对了没有」很难自动判定；所以才需要轨迹、评测集和回归门禁。

**Agent = 一个由模型决定下一步的循环；工程上的一切，都是在决定每一轮让模型看到什么，以及让它的决定在什么边界内变成现实。**
